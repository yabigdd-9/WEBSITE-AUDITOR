A10 — DLQ provider-outage tagging evidence
==========================================

Mechanism: mm_pipeline.fail() accepts provider_state and lane kwargs; they are
merged into the existing pipeline_items.payload JSON (no DDL/schema change).
When a handler raises an error that dead-letters an item, the provider_state
and lane tags are stored inside payload. ./mm dead-letter can then separate
infrastructure deferrals from prospect-quality failures with a single query:

  SELECT business_id FROM pipeline_items
  WHERE state='PERMANENT_FAILURE'
  AND json_extract(payload, '$.provider_state') IS NOT NULL
  AND json_extract(payload, '$.lane')='search'

Test: test_dead_letter_distinguishes_provider_outage_from_prospect_failure
  Creates two businesses enqueued with max_attempts=1.
  - Outage item: p.fail(..., RetryableError('search provider absent'),
      retryable=False, provider_state='BLOCKED_SEARCH_SERVICE_ABSENT', lane='search')
  - Prospect item: p.fail(..., PermanentError('unfixable prospect'), retryable=False)

Assertions:
  outage item state == PERMANENT_FAILURE
  prospect item state == PERMANENT_FAILURE
  outage payload.provider_state == 'BLOCKED_SEARCH_SERVICE_ABSENT'
  outage payload.lane == 'search'
  prospect payload has no provider_state
  prospect payload has no lane
  single json_extract query returns exactly [outage business_id]
